## Proposed classification policy

The requested historical table is supported for the documented integer examples: 1–3 Poor, 4–6 Fair, 7 with UsageClass L Good, 7 with P/S Fair, 8–10 Good. This is **not an approved policy for 6yyb-pb25**.

`services/pavement_verification.proposed_legacy_classification` tests a literal interval interpretation for review: 1≤r≤3 Poor; 4≤r<7 Fair; r=7 uses the explicitly supplied P/S/L value; 8≤r≤10 Good. Fractional (3,4) and (7,8), missing/invalid scores and unsupported local-7 usage remain Unknown. No rounding, interpolation, inferred UsageClass or PCI conversion occurs. The function always reports `applicable_to_current_feed=false` and `Proposed — Pending Review`; it is used only by offline audit tests, never the road summary/API/importer. Recognized source categories are compared; disagreements retain both source and computed values and yield Unknown. Unsupported source category text is retained with an explicit reason.

For the actual feed, SystemRating is described as 1.00–10 with two decimal places; the dictionary’s category column also includes 0–3, contradicting its scale description. The local-7 exception has no supporting UsageClass field; Road_Type describes roadbed type. NonRatingReason may accompany a numeric score. These unresolved semantics keep **every active category Unknown**, including apparently straightforward integer examples; the active complete-policy gate has not passed. Raw scores remain unchanged. No source-category disagreements can be assessed because this feed has no category column and no approved computed policy.

## Matching policy and release differences

The existing overlay uses projected ≤5 m proximity, OFT first-six-digit street-code evidence, on-street name agreement, buffered coverage fractions and the full competing set. The 5 m buffer is an application candidate assumption, not measured source accuracy or an acceptance cutoff. Source direction/road type are retained. Grade and roadbed agreement stay unknown. From/to names and LION NodeIDFrom/NodeIDTo are retained in archived inputs but node/alias/cross-street/angle compatibility is not yet established by this extract. No new automatic rule is authorized.

The audit’s identifier helper accepts ASCII digit strings of length 1–7 and zero-pads to seven characters, rejecting numeric coercion, decimal/exponent/non-ASCII/overlength inputs. This verifies syntax only, including for `0000000`; it does not establish existence or validity in an edition. Raw IDs remain unchanged. The existing importer’s SegmentID:OBJECTID row identity remains authoritative for stored row identity; no renumbering or deduplication occurs.

An ID-only crosswalk is inapplicable: all pavement records lack SegmentID. Even for a future feed with SegmentID, require exact referenced LION edition/revision, source dictionary, duplicate-row analysis and geometry/node/roadbed scope. Archive applicable LDF headers and the complete relevant release chain to detect retired/split/merged/changed segments. Changed geometry/nodes with persistent IDs require scope review, not automatic identity rejection or acceptance. Missing LDF/reference release means compatibility unknown, not zero changes. The 505 repeated IDs have identical normalized geometry and node values within each group in this extract; that does not establish grade, administrative equivalence or compatibility with pavement acquisition.

Every accepted overlay decision still needs an authorized human review binding base snapshot, full source/target hashes, candidate/parameter hashes, scope, reviewer, rationale and evidence references. A nearest candidate, a single candidate, matching name/code or 100% buffered overlap cannot satisfy that requirement. New decisions create a new immutable release, with no original-row/match rewrite or automatic activation.
